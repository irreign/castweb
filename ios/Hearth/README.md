# Hearth iOS (SwiftUI, MVVM)

See `docs/` at the repo root for product/architecture context. This is the
setup and structure reference for the client.

## Opening the project

This repo ships the project as an [XcodeGen](https://github.com/yonaskolb/XcodeGen)
spec (`project.yml`) rather than a checked-in `.xcodeproj` — the generated
project file is derived, machine-specific noise that doesn't belong in
version control.

```bash
brew install xcodegen
cd ios/Hearth
xcodegen generate
open Hearth.xcodeproj
```

Then in Xcode: File → Packages → Resolve Package Versions (pulls in
`supabase-swift`), fill in `Config/Dev.xcconfig` with your local/dev
Supabase project's URL and anon key (see supabase/README.md), and Run.

## Structure (docs/04-technical-architecture.md §4.3)

```
Sources/Hearth/
  App/              app entry, root state, tab/navigation coordination
  Core/Models/       Codable structs mirroring the Postgres schema
  Core/Services/      thin wrappers over the Supabase SDK — one per
                      domain (Auth, Family, Chat, Calendar, AI, Notification)
  Core/Utilities/      date/JSON helpers, ServiceError, Haptics, Permissions
  Features/Auth/       Welcome, Sign in/up, onboarding (create/join family)
  Features/Chat/        the message list, composer, and the 4 AI card types
  Features/Calendar/    month/agenda views, event detail/edit
  Features/Family/      member list, invite
  Features/Settings/    account, notifications, AI behaviour, calendar prefs, privacy
  Resources/           Assets.xcassets (Info.plist/entitlements are
                        generated by XcodeGen from project.yml, not
                        checked in)
HearthTests/          unit tests for pure logic (CalendarDate/ClockTime,
                       Permissions, chat day-grouping) — no network/SDK
                       dependency, run with the `Hearth` scheme's Test action
```

## What has and hasn't been verified

Every file here is real, complete Swift written against supabase-swift
v2's documented API shape — not pseudocode. It has **not** been compiled
by Xcode in this environment (no macOS/Xcode toolchain is available where
this was written — see docs/09-development-plan.md "what could not be
verified"). The highest-risk integration points, called out inline where
they occur, are:

- **`SupabaseClientOptions` shape** (SupabaseManager.swift) — the
  `db`/`auth` sub-option initializers should be checked against the
  exact pinned `supabase-swift` version.
- **Realtime API** (ChatService.swift) — `realtimeV2`/`postgresChange`/
  `AnyAction` reflect the documented v2 surface at the time of writing;
  verify case names against the pinned version.
- **`FunctionsError` shape** (EdgeFunctionsClient.swift) — error-body
  extraction is left as a `TODO` rather than guessed, since getting this
  wrong silently would be worse than an honest gap.

None of these affect the *design* — the service layer's public API
(`AuthService`, `FamilyService`, `ChatService`, `CalendarService`,
`AIService`, `NotificationService`) is stable regardless of what's inside
each method, so fixing a compile error in one of these three spots means
editing that method's body, not any call site.

## Why XcodeGen instead of a hand-maintained `.xcodeproj`

A hand-edited `project.pbxproj` is exactly the kind of file that's
miserable to write correctly without Xcode itself generating it, and
brutal to code-review or merge-conflict-resolve as text. `project.yml` is
~80 lines, human-readable, and regenerates deterministically — the
standard solution for keeping an Xcode project's *structure* (not its
build artifacts) in version control.
